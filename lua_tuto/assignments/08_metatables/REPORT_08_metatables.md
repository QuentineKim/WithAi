### 1. 문제 2·4에서 프록시를 빈 테이블로 만든 이유 (`__newindex` 호출 조건)

Lua의 `__newindex` 메타메서드는 테이블에 **존재하지 않는 키(값이 `nil`인 키)**에 대입할 때만 호출되며, 이미 값이 들어 있는 키를 덮어쓸 때는 호출되지 않습니다.
만약 `M.readOnly(t)`(`18~25줄`)나 `M.tracked(t, onChange)`(`82~96줄`)에서 원본 테이블 `t` 자체에 메타테이블을 붙이면, 기존 키(예: `maxHp`, `hp`)를 수정할 때 `__newindex`를 거치지 않고 바로 덮어써집니다.
따라서 반환하는 프록시를 항상 빈 테이블 `{}`로 두고(`19줄`, `83줄`), 읽기는 `__index = t`(`20줄`, `84줄`)로 위임하며 쓰기는 항상 `t`에만 반영(`90줄`)해 프록시 자신을 비워 둡니다.
그 결과 기존 키든 새 키든 프록시 입장에서는 항상 없는 키에 대한 쓰기가 되어 매번 `__newindex`(`21줄`, `85줄`)가 정상적으로 실행됩니다.

### 2. 문제 3에서 `2 * s`가 동작하는 이유 (`__mul`의 인자 순서)

Lua는 이항 연산 `a * b`를 평가할 때 왼쪽 피연산자 `a`의 메타테이블에서 `__mul`을 먼저 찾고, 없으면 오른쪽 피연산자 `b`의 메타테이블에서 `__mul`을 찾아 호출합니다.
`2 * s`에서 숫자 `2`에는 `__mul` 메타메서드가 없으므로 오른쪽 피연산자 `s`의 메타테이블(`Stats`)에 정의된 `Stats.__mul(a, b)`(`55~62줄`)이 호출됩니다.
이때 메타메서드 인자는 피연산자 위치 그대로 넘어가므로 `s * 2`는 `(s, 2)` 순서로, `2 * s`는 `(2, s)` 순서로 전달됩니다.
`Stats.__mul`에서 `type(a) == "number"`(`56~57줄`)와 `type(b) == "number"`(`58~59줄`)를 모두 분기해 처리했기 때문에 두 순서 모두 스칼라 곱이 동작합니다.

### 3. `rawget` / `rawset`을 써야 하는 상황

`rawget`과 `rawset`은 `__index`, `__newindex` 메타메서드를 우회해 테이블 자체의 실제 키를 읽거나 쓸 때 사용합니다.
예를 들어 `M.withDefaults(t, defaults)`(`11~13줄`)는 `__index = defaults`가 걸려 있으므로 `t.hp`를 읽으면 기본값이 반환되지만, `rawget(t, "hp")`를 쓰면 `t` 자체에 `hp`가 저장되었는지(`nil`인지) 확인할 수 있습니다.
또한 `Stats.new` 인스턴스(`40~44줄`)에 메서드가 복사되지 않았는지 검증할 때도 `rawget(s, "power")`로 `__index` 위임을 건너뛰고 확인합니다.
쓰기 측면에서는 `M.readOnly(t)`(`21~23줄`)처럼 `__newindex`가 에러를 내거나 자기 자신에 값을 기록해야 하는 메타메서드 내부에서 일반 대입 대신 `rawset`을 써야 에러나 무한 재귀를 피할 수 있습니다.

### 4. Lua 5.1의 `__len` 미지원 우회 선택

Lua 5.1에서는 테이블에 `__len` 메타메서드를 정의해도 `#t` 연산자가 이를 호출하지 않고 테이블 자체의 배열 길이만 계산합니다.
그래서 이 과제에서는 길이나 개수를 `#proxy`나 `#Enemy`에 의존하지 않고, 문제 5에서 생성된 적 총수를 `Enemy.count` 필드(`105줄`, `114줄`)로 별도 관리했습니다.
문제 2·4의 빈 프록시(`19줄`, `83줄`) 역시 `#proxy`가 항상 `0`이 되므로 키 개수가 필요하면 `pairs`로 원본을 순회하거나 `:size()` 같은 별도 메서드를 두는 방식을 선택합니다.
문제 3의 `Stats`(`40~44줄`) 또한 배열 길이가 아니라 고정 필드(`hp`, `atk`, `def`)와 `Stats:power()` 메서드(`72~74줄`)를 직접 사용하도록 설계해 `#t`에 의존하지 않았습니다.
